> **This is an AI review (Grok Bot), not a human or professional audit. It carries no assurance, was performed by the same AI toolchain family that wrote earlier versions
> of this code, and is NOT a substitute for an independent audit and legal review. Nothing is deployed; the mainnet flag remains OFF; no funded keys were used.**

## v3 scope & method
Fresh read of `Paper10kExchange`, `HyperCoreOracle`, `PythReference`, `Paper10kX`, `Deploy.s.sol` against: reentrancy, oracle manipulation, queue/IOU accounting, insurance fund, timelock coverage, mint abuse, rounding, DoS, liquidation griefing.
Tooling re-run: `forge test` (48 tests; fuzz 5,000 runs, invariants 300×depth 100) all pass; Slither 0.11.6 `--filter-paths "lib|test|script"` → **0 high / 0 medium**, only the previously accepted informational/low classes (timestamp, strict `== 0`, low-level call, costly-loop, unindexed addresses, one missing event on `PythReference.setMaxConfBps`).

## v3 findings
| # | Sev | Finding | Status |
|---|---|---|---|
| F1 | **Medium (trust/timelock bypass)** | `HyperCoreOracle.configure` / `setGuards` were **instant** `onlyOwner`. The exchange's "everything economic is timelocked" claim therefore had a hole: whoever owns the oracle could remap a live market (e.g. BTC → a thin asset, or a wrong `szDec` → 10× price) or loosen the spread/deviation guards with no notice, then open/liquidate. The launch doc only *asked* that the oracle owner be the same timelock. | **Fixed.** Oracle now has an immutable `delay` (≥5 min, mainnet script passes the config delay ≥1 day), instant `configure/setGuards` only during a one-way `bootstrapped=false` window, `finalizeBootstrap()` then `proposeMarket/applyMarket/cancelMarket` and `proposeGuards/applyGuards/cancelGuards`. Launch runbook: call `finalizeBootstrap()` **before** `unpause()`. Tests: `AuditV3Test.test_oracleConfigTimelockedAfterBootstrap`, `…OnlyOwnerProposes`, `…DelayFloor`. *Residual:* before `finalizeBootstrap()` the owner is trusted (exchange is paused then); a forgotten finalize is an operational risk the checklist must tick. |
| F2 | Low | Exchange `configDelay` could be deployed as `0` (timelock = no-op) — the ≥1 day rule was only in the script. `renounceOwnership()` (inherited) on a paused exchange would strand open positions (no `unpause`, no emergency mode). | **Fixed:** constructor requires `configDelay ≥ 5 min`; `renounceOwnership` reverts. Test `test_exchangeDelayFloorAndNoRenounce`. |
| F3 | Low (unreachable in practice) | `notional = margin × leverage` was cast to `uint128` unchecked; with `maxMarginPerPosition` ≥ 2^128/10⁴ the notional would truncate silently (OI and PnL would be understated). Unreachable with 6-dec USDC, but a config mistake could reach it. | **Fixed:** explicit `notional ≤ uint128.max` check. Test `test_hugeNotionalRejected`. |
| F4 | **Medium (parameter / design)** | **Deadband default too weak.** Default `deadbandWad = 2e12` = **0.0002 % = 0.02 bps**. The BBO mid can be jittered by resting an inside quote (half-spread ≈ 0.1–0.25 bps on BTC/ETH). Papertrade's own docs use a **0.2 bps** deadband for precisely this reason. A trader who nudges the mid by one tick, opens, then profits when it reverts exceeds our deadband at 10,000× (1 bp ≈ 100 % of margin gross, haircut-reduced). minHold/same-block rules slow this but do not remove it. | **Mitigated:** mainnet deploy script now **refuses a deadband < 0.2 bps** (`2e13`). Test/default values for testnet unchanged. *Not solvable in code:* any single-venue mid has some jitter edge; needs live tuning and OI/margin caps (MAINNET_LAUNCH). |
| F5 | Medium (design, documented) | **Liquidation griefing by jitter.** Bust distance at 10,000× / 10 % maint is **0.009 %** (0.9 bps) — comparable to a few ticks of BBO jitter. An attacker can briefly shift the mid with a non-filling quote and `liquidate()` victims' 10,000× positions (public, no bounty, margin forfeited to the pool; victim also gets PAPER10KX). Beneficiary is only the pool (owner/stakers/seeders), but it is real user harm. HyperCoreOracle's spread ≤30 bps and ±100 bps vs `oraclePx` guards do **not** bound a ~1 bp shift. | **Documented, not fixed in code.** Options (design change, need your decision): liquidation only after a price-breach has persisted across ≥2 distinct blocks (two-step `markLiquidatable`/`liquidate`), cap max leverage on mainnet to ≤1000× (bust 0.09 %), or tighten `maxDevBps`/use `Mark` precompile as a second reference. Recommend lowering mainnet `maxLeverage` until measured. |
| F6 | Low (doc error) | v2 text said win fees "flow into" the insurance fund. They do not: the fee is simply not paid out (stays in `pool`); insurance is fed only by `insuranceBps` of forfeited margin/losses and donations. | **Doc corrected** here (no code change). |
| F7 | Info | **Exposure is not reserved against open positions.** `applyWithdraw` only refuses while `queuedTotal != 0`; after the delay the owner may withdraw all of `pool` even while open positions could win up to 100× margin. Visible on-chain during the delay, but users cannot be assumed to watch. | Accepted/trust assumption; recommend a rule "withdraw ≤ pool − k·Σ open capped liabilities" or a larger delay for withdrawals. |
| F8 | Info | Oracle fail-closed is symmetric: when guards trip (violent market), **no one can close, liquidate or open**; positions that were busted during the halt may be "saved" by a later price. `emergencyCancel` (owner-enabled, paused only) lets *busted/losing* users cancel at entry as well. | By design; documented. |
| F9 | Info | Queue dust spam: each winning close that cannot be paid appends an entry (gas cost to the attacker ≥ cost to process). No loop is uncapped (`processQueue(maxEntries)`), FIFO preserved (test `test_queuePartialFIFOAndAccounting`). | Accepted. |
| F10 | Info | Collateral-token risk: USDC blacklisting of the exchange address would freeze everything; guardian can grief by pausing/closing markets (cannot steal); `rescueToken` correctly excludes collateral. | Accepted. |

## Checked and found OK (fresh-eyes pass)
**Reentrancy:** every state-changing external path is `nonReentrant`, effects before the only external calls (token transfer, `px.mint` to a trusted token); `PythReference` uses try/catch. **Cash conservation:** each flow moved pool/insurance/free/margin by equal and opposite amounts (also asserted by the existing exact invariant). **Queue/IOU:** strict FIFO (new winners go to the back whenever the queue is non-empty, even if the pool has cash), `queuedTotal == Σ queuedOf == Σ entries`, partial head payment keeps position, owner withdrawals blocked while owed, insurance only pays after pool is empty. **Insurance:** can only be reduced by paying winners/queue or a timelocked withdraw when nothing is owed. **Mint abuse:** only the exchange (minter locked) mints, only on liquidation, supply capped, never reverts on the cap; self-liquidation farming costs the forfeited margin (a long+short pair loses ≈½ of margin per mint even in the best case). **Rounding:** all roundings favour the pool by <1 wei, `m ≥ 1` after the deadband so the haircut denominator cannot divide by zero, `mulDiv` throughout. **Owner powers after v3:** instant = pause/closeMarket/guardian only (safety-reducing); everything economic, the oracle, and house-capital withdrawals are timelocked; positions keep their params version.

## Not verified (v3)
HyperCoreOracle in-EVM behaviour on real HyperCore state (no fork tooling); gas of precompile reads; guard thresholds/deadband under real data; Pyth address/ABI; behaviour of the Timelock/multisig that will own it; no formal verification; no independent human audit; no legal review; the frontend was not re-audited in this pass. Fuzzing found no new failures, but passing tests ≠ absence of bugs.

# AUDIT.md — AI self-audit of the PAPER10K contracts (v2, after remediation)

> **This is an AI-generated self-audit by the same agent that wrote the code. It is NOT an independent audit, carries no assurance, and is NOT a
> substitute for a professional audit (and legal review) before any mainnet use.** Several issues are *design-level risks that cannot be fixed in code*.
> v1 findings are kept below with their v2 status. Nothing has been deployed to any mainnet.

## v2 summary — what changed (remediation round)
| v1 # | Fix in v2 |
|---|---|
| 1 latency arb | **Oracle replaced.** Mainnet uses `HyperCoreOracle`: a *pull* read of the HyperCore BBO precompile (`0x…080e`) and `oraclePx` (`0x…0807`) **inside the trade transaction** — no price is ever pushed, so there is no stale-price window. Guards (fail closed → price 0 → trade reverts): spread ≤ 30 bps, crossed/zero book, |mid − oraclePx| ≤ 100 bps, optional second reference (`PythReference`, conf + staleness + deviation). Win-side "spread": deadband (default 0.0002 %) zeroes tiny wins plus the haircut; `minHold` 3 s and a same-**block** open/close ban. *Residual:* a trader with faster off-chain information than HyperCore's own book still has an edge for moves ≥ deadband; tune with real data. |
| 2 insolvency | **Insurance fund** (`fundInsurance`, `insuranceBps` = 10 % of forfeited margin/losses; *v3 note: win fees do NOT flow in*). Wins are paid pool → insurance → FIFO queue. Insurance withdrawal is timelocked and blocked while the queue is non-empty. Exact-equality cash-conservation invariant added. *Residual:* correlated wins can still exceed pool + insurance (queue); sizing in MAINNET_LAUNCH §4. |
| 3 owner power | **Versioned parameters + timelock.** `maintBps, fees, haircut rate, deadband, profit cap, mint rate, leverage cap, margin limits` live in a `Params` history; every position stores the version it opened under, so **a config change cannot alter an open position's bust price or payout** (fuzzed + invariant `bustFrozenAtOpen`). `proposeConfig/applyConfig`, `proposeMarket/applyMarket`, `proposeOracle/applyOracle`, `proposeWithdraw/applyWithdraw` all wait the immutable `configDelay` (mainnet script enforces ≥ 1 day; launch doc says 2 days). Instant powers are only safety-reducing: `pause`, `closeMarket` (guardian too). *Note:* `Ops` (deposit cap, `maxPriceAge`, `minHold`) are applied with the same timelock but are operational limits that also affect open positions' close timing (not their economics). |
| 4 signed oracle | `SignedPriceOracle` and `TestUSDC` moved to `src/testnet/`; **the Deploy script refuses them on chain 999**. |
| 5 maint snapshot | Subsumed by versioned params. |
| 6 oracle freeze | No jump guard in the primary oracle (gaps are real). If a guard trips, trading halts but `withdraw` of free balance and `emergencyCancel` keep working; owner can swap oracle after the delay. |
| 15 untested adapter | Precompile layouts **verified live with `eth_call` against the public HyperEVM RPC** (BBO → `(uint64 bid, uint64 ask)`, oraclePx → `uint64`, scale `10^(6−szDecimals)`; BTC szDec 5, ETH 4). Mock-precompile unit tests cover every guard. *Still not run in a HyperEVM fork test or deployed — see "Unverified".* |

## Scope & method (v2)
`contracts/src/*.sol` (Solidity 0.8.26, OpenZeppelin 5.1.0 vendored). Slither 0.11.6 re-run: `slither . --filter-paths "lib|test|script"` → **0 high, 0 medium actionable**.
Remaining detector output: `timestamp`, `low-level-calls` (the intentional precompile `staticcall`), `costly-loop` (queue processing, caller-bounded), `incorrect-equality` (`== 0` sentinel checks only), `missing-zero-check` (`setGuardian(0)` intentionally disables the guardian; `setMinter` locks), unindexed event addresses, one missing event on `PythReference.setMaxConfBps`. All accepted.

Tests: `forge test` → **41 tests** (unit, governance/timelock, oracle guards with mock precompiles, Pyth adapter, token, 7 fuzz properties, 9 stateful invariants). Run at 5000 fuzz runs and 300 × depth-100 invariant runs: clean. Coverage: Exchange 98 % lines / 95 % statements, HyperCoreOracle 100 % lines, total 85 % (testnet-only helpers lowest).
Invariants: exact cash conservation (`balance == free + margin + pool + insurance`), users always fully backed, Σ position margins == `totalMargin`, queue sum, free-balance sum, OI == Σ notionals, **bust price frozen at open under random config changes**, params version monotone, PAPER10KX supply ≤ cap.
Mutation checks: (a) double-counting liquidation margin into the pool → caught by 3 unit tests, the conservation invariant and a fuzz test; (b) `unpause` not clearing emergency mode → was **not** caught, so `test_unpauseClearsEmergencyMode` was added.
Fuzz properties: settlement ≤ margin·(1+cap) and solvent for any leverage/side/move; wins monotone in move; bust distance = (1−maint)/lev; random valid config never changes an open position's bust or payout; deposit/withdraw accounting; owner withdrawal bounded by pool/insurance; PAPER10KX mint exact.
Also verified end-to-end on local anvil (public dev keys only) through the real UI: connect, wrong-network prompt, sign-in, faucet, deposit, open, liquidation minting PAPER10KX.

## Unverified / not done (be explicit)
1. `HyperCoreOracle` has **never executed against real HyperCore state inside the EVM** (no fork test possible here; Foundry's EVM has no HyperCore precompiles). Only the byte layouts were checked via raw RPC. Gas use of the precompile reads and behaviour at block boundaries are unmeasured on-chain.
2. `PythReference`: the Pyth contract address on HyperEVM and the `getPriceUnsafe` ABI were **not verified** (address only seen truncated). It is optional and off by default; do not enable until verified from Pyth's official address list.
3. Guard thresholds (30 bps spread, 100 bps oraclePx deviation, 0.0002 % deadband, 3 s hold) are untuned; a single live sample showed book-vs-`oraclePx` deviation ≈ 4.5 bps (BTC) / 4.7 bps (ETH) and spreads < 0.5 bps, so 100 bps is generous; it may still halt trading in violent markets (fails safe, a liveness cost). One sample is not tuning.
4. No public-testnet deployment (no faucet-funded throwaway key could be obtained safely), WalletConnect never tested with a real wallet.
5. Latency arbitrage is *reduced and priced*, not eliminated. Keeper liquidation ops/incentives are not built (anyone can call `liquidate`; no bounty).
6. Independent audit, legal review, owner multisig/timelock setup, USDC address verification: all still required.
